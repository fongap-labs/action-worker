# 定时派发状态历史与安全去重

自动任务与定时部署在调用 GitHub `repository_dispatch` **之前**，先写入签名的 `pending` 调度回执；只有确认调用被接收后再写 `success`。两种回执都能阻止重复派发。不能因为某个派发失败或执行失败便删除、覆盖或忽略历史回执。

## 历史扫描范围

- 按调度槽位寻找在该时刻可能记录回执的默认分支提交，包含运行时的 HEAD 及槽位前最后一个 HEAD。
- 对每个候选 SHA 使用 GitHub `commits/{sha}/statuses` 的完整历史，绝不使用只保留每个 context 最新记录的合并 `/status` 来证明没有派发。
- GitHub 文档明确该接口按**逆时间顺序**返回。每页必须是结构有效的记录；对准确的回执匹配还必须验证签名、context、状态和原始描述。
- 若给定槽位，只有当**整页**含完整且严格按时间降序排列的有效 `created_at`，且最老一条早于槽位时间减去五分钟容差，才可以断定后续页面不可能含有该槽位正常产生的回执，并安全停止搜索。必须先查找并接受本页内所有有效签名回执。
- 时间戳缺失、日期无法解析或顺序不可信的页面**不能用来提前停止**，仍须继续枚举；实际枚举超过每 SHA 50 页（5,000 条状态）仍按退出码 75 拒绝，绝不据此执行可能重复的业务任务。

## 运行故障与验收

[2026-11-09 调度运行 #42552529931](https://github.com/fongap-labs/action-worker/actions/runs/42552529931) 的 `Scheduled task projects` 在旧 1,000 条上限触发退出码 75，阻止了派发。这是正确的拒绝重复执行机制，但在活跃历史里导致计划任务持续阻塞；源码修复通过槽位时间界限缩短必要扫描，同时保留完整签名校验与硬上限。

源码合同测试覆盖超过旧 1,000 条上限后的提前安全截止、截止页内的有效 `pending` 回执、乱序历史不可截断、无日期历史仍按硬上限拒绝。**这些测试不等于真实计划任务恢复**；需要受控核对合并后实际调度运行及其状态回执，不要手动重放已预留的槽位或解除失败保护。
