# 共用治理规范

## 1. 权威归属

跨仓库规则只在中央维护。

### ❌ 错误做法 / 反面教材

每个项目复制一套治理规则。

```text
业务仓库甲/docs/治理规范.md
业务仓库乙/docs/治理规范.md
```

### ✅ 正确做法 / 规范范例

中央定义，项目只引用。

```text
action-worker/docs/01_SHARED_GOVERNANCE.md
业务仓库/CLAUDE.md → 共用规范 + 项目专属规范
```

## 2. 文档语言

治理说明只写中文。

### ❌ 错误做法 / 反面教材

标题中英混排，正文重复翻译。

```markdown
## 快速开始（Quick Start）
This policy applies to all repositories.
```

### ✅ 正确做法 / 规范范例

中文标题、中文规则、原样代码标识符。

```markdown
## 快速开始
所有受管仓库统一使用中央合并门禁。
```

治理文档不建立双语镜像。二、三级标题只用中文；规则直接陈述，优先给出错误与正确范例。源代码、机器协议、配置键及执行日志保持其原生格式，不改写固定标识符。

## 3. 权威顺序

冲突时以机器合同为准。

### ❌ 错误做法 / 反面教材

让项目说明覆盖共用门禁。

```text
项目文档 → 忽略中央安全门禁
```

### ✅ 正确做法 / 规范范例

按唯一权威顺序裁决。

```text
合同/策略/规则 → 中央共用规范 → 项目边界 → 项目文档 → 示例
```

项目规则可以收紧，不得绕过中央约束。

## 4. 合并门禁

未通过中央门禁不得合并。

### ❌ 错误做法 / 反面教材

把智能体审查当成合并许可。

```text
智能体审查通过 → 合并
```

### ✅ 正确做法 / 规范范例

确定性检查全部成功才授权。

```text
安全校验 + 中央持续集成证据 + 合并请求策略
                ↓
          validate-merge
                ↓
               合并
```

智能体审查只提供建议；它不能替代安全、证据或合并门禁。

## 5. 主分支可信性

来源未经证明的提交不得发布。

### ❌ 错误做法 / 反面教材

直接写入主分支并部署。

```bash
git push origin HEAD:main
```

### ✅ 正确做法 / 规范范例

合并后校验来源，再执行特权任务。

```text
合并请求 → 中央门禁 → 合法合并 → 主分支来源证明 → 发布/部署
```

`07_MAIN_WRITE_GUARD.md` 定义详细证明规则。私有仓库缺少原生分支保护时仍必须经过中央治理；不得把提醒标签当作强制保护。

## 6. 执行与密钥

重型任务与凭据统一管控。

### ❌ 错误做法 / 反面教材

业务仓库自建中央任务与密钥回退。

```text
业务仓库 → 自建发布链 → 个人令牌自动回退
```

### ✅ 正确做法 / 规范范例

业务仓库只保留薄入口。

```text
业务仓库入口 → Action Worker → 受限执行器
                         ↓
                  独立最小权限凭据
```

缺少专用凭据必须明确失败。执行合同见 `EXECUTION_CONTRACT.md`，运行器规则见 `RUNNER_POLICY.md`。

## 7. 规则与测试

重要规则必须对应机器校验。

### ❌ 错误做法 / 反面教材

只修改说明文字。

```text
修改治理文档 → 直接合并
```

### ✅ 正确做法 / 规范范例

策略、实现、测试和文档同步。

```text
机器合同/策略 → 校验脚本 → 合同测试 → 治理文档
```

配置名称见 `03_NAMING_CONVENTIONS.md`；变更类型和中文日志见 `04_CHANGELOG_CONVENTIONS.md`。

## 8. 项目责任

业务仓库只维护项目专属内容。

### ❌ 错误做法 / 反面教材

复制组织级命名、门禁和发布规则。

```text
项目规则 = 共用命名 + 共用门禁 + 项目实现
```

### ✅ 正确做法 / 规范范例

项目独立定义产品与运行时。

```text
项目规则 = 产品边界 + 对外协议 + 专属测试 + 实现约束
```

新增共用规则必须先修改 Action Worker；不为每个仓库创建第二份权威。

## 9. 构建、测试和发布的中央归属

共用工程能力只在 Action Worker 中实现；业务仓库仅维护产品源码、锁定依赖、
编译器配置及确实不能外置的产品专属构建参数。业务仓库不可另建独立的 CI、
测试执行器、通用构建器或发布/部署编排，也不得在 PR 内自行降低中央门禁。

- 通用构建器、测试基础设施、可外置的业务回归测试、发布编排及凭据策略归中央。
- 产品专属编译配置（如 `tsconfig.json`、Cargo 清单、依赖锁文件）随源码版本管理。
- 必须在仓库中执行的 Rust crate、桌面 UI、特权基础设施测试可保留，但例外的
  仓库及路径只能在中央 `policies/engineering-ownership.json` 中批准并说明原因。
- 禁止新增项目内 `tests/` 测试源码、`*.test.*` 等测试，以及本地
  `central-ci*` 执行入口；新增可外置测试一律进入 `tests/packs/<pack>/`。
- 业务仓库只能使用 `templates/bridge/` 中可信版本的薄工作流；不得自行新增或
  修改为可执行产品构建、测试和发布的 Actions 工作流。
- 现存未迁移测试属于待收敛债务，不构成新增测试的永久豁免；迁移须先记录基线，
  在中央测试包通过验证后，才可删除业务仓库中的原件。

### 门禁

中央 CI 准备阶段在所有路由（包括原生私有 CI）使用可信 Action Worker、
GitHub 只读比较 API 与 `base/head` 不可变提交运行
`scripts/central-engineering-gate-api.ts`；Linux 沙箱另以真实 Git 差异运行
`scripts/central-engineering-gate.ts`，在项目源码执行前再次确认。业务 PR 修改自身测试、策略文件或
工作流，不能改变此项判定。新增本地工程基础设施、未经批准的工作流或
新测试文件将使 CI Evidence 失败，`validate-merge` 因而不得放行。

仅改文档不构成豁免。确需新增例外时，必须先在 Action Worker 提交可验证的
中央策略与测试，并说明为何中央无法独立执行，不允许在业务仓库声明例外。
详细执行与迁移见 `05_INTEGRATION_GUIDE.md`、`TEST_PACKS.md`。
