# Fongap Labs 共用治理

本文件定义 Fongap Labs 受管仓库共用的工程治理。**凡是适用于两个或以上仓库的规则，首先在 Action Worker 中维护**；业务仓库只保留仅属于本项目的产品、架构、运行时与边界规则。

---

## 1. 权威边界

```
Action Worker
= 共用治理
+ 机器合同 / 策略 / 规则
+ 统一执行平面
+ PR / CI / Review / Build / Release / Deploy / Task 治理
+ Runner 解析与执行 provenance

业务仓库
= 产品源码
+ 产品测试
+ 项目架构
+ 项目专属脚本与边界
+ 执行清单
+ 薄的集成工作流
```

业务仓库**不得复制** Action Worker 已定义的通用命名、变更分类、PR 门禁、执行治理、Release 治理、Repository Policy 或 Agent 工程规则。

公开仓库与私有仓库使用同一套执行架构。除 GitHub 平台要求目标仓库自行创建的最薄分发与桥接检查之外，**所有重型执行（CI、测试、构建、AI Review、Release、Deploy 与定时任务）都进入 Action Worker**。仓库可见性只能影响访问方式与 GitHub 平台保护功能，不得形成第二条执行路径。

统一执行边界由 `EXECUTION_CONTRACT.md` 定义；Runner 抽象与 self-hosted 边界由 `RUNNER_POLICY.md` 定义。

## 2. 语言与文档分层（唯一权威）

| 文档类型 | 语言 | 说明 |
|----------|------|------|
| **机器读取文档**（`contracts/`、`policies/`、`rules/`、`skills/`、`CLAUDE.md`、`AGENTS.md`） | **英文** | 精确、无歧义、结构化（编号/代码块/显式条件分支）、可验证（有合同测试） |
| **人类阅读文档**（`README.md`、指南、治理文档、`proposals/`） | **中文** | 单一文件，无镜像；先说“是什么”，再讲“怎么做”；每个术语首现时解释；用示例代替抽象；不假设读者懂 GitHub Actions；分层组织（初学者/维护者）；一段只表达一件事 |
| **工程产出**（PR 标题、CHANGELOG 条目、代码注释、工作流名称/步骤、日志、错误信息、测试描述、配置键） | **英文** | 严禁中英混用 |
| **例外** | — | 面向用户的界面文案、本地化资源、纯数据文件（`.txt/.csv/.tsv`）、HTML 模板标签间文案（模板注释保持英文） |

> **所有其他文档中的语言规则均以本节为准**；其它文档仅保留“参见 `01_SHARED_GOVERNANCE.md §2`”。

## 3. 共用规则

Action Worker 为所有受管仓库维护以下规则：

- 仓库治理与合并默认值（见 `02_REPOSITORY_GOVERNANCE.md`）
- 命名约定（见 `03_NAMING_CONVENTIONS.md` 与 `TERMINOLOGY.md`）
- CHANGELOG 与 PR 变更分类（见 `04_CHANGELOG_CONVENTIONS.md`）
- 工程 diff、PR 标题、CHANGELOG 条目与 Release 摘要使用英文（§2）
- 通用开发与验证规则
- PR 治理与合并门禁合同（见 `02_REPOSITORY_GOVERNANCE.md` §3）
- 公开仓库与私有仓库统一的执行合同（见 `EXECUTION_CONTRACT.md`）
- 中央 CI / 构建 / 审查 / 发布 / 部署 / 任务执行
- Runner Profile、Runner 解析与自托管边界（见 `RUNNER_POLICY.md`）
- 发布与部署治理（见 `06_RELEASE_DEPLOY_GUIDE.md`）
- Release 的应用版本，**仅来自发布启动时输入的版本**（不得由仓库文件版本字段、manifest、CHANGELOG 标题、文件一致性检查或上次发布比较决定）
- 跨仓库的信任与密钥边界
- 通用 Agent 入口与优先级规则（见 §5）
- 跨仓库的语言与运行时收敛规则

**语言治理长期原则**：先保证小内核与大框架，再考虑单一语言目标。语言选择跟随模块边界。在性能、安全、功能、兼容性与可维护性不下降的前提下，优先移除不必要的语言与运行时；但**禁止仅为“统一技术栈”而重写边界清晰的稳定实现**。跨语言的重复权威、重复状态与重复协议优先消除。

## 4. 项目本地规则

业务仓库只保留**没有该项目就不可能存在**的规则，例如：

- 产品定位与产品边界
- 运行时、协议与公开 API 架构
- 仓库专属的依赖规则
- 产品专属的安全不变式
- 项目的发布兼容性
- 能力或扩展边界
- 项目专属的构建、打包与部署实现

**判断标准**：
> 如果一条规则去掉项目名之后仍然适用于其他仓库，它通常不应留在业务仓库中。

## 5. 权威顺序

发生冲突时，按以下顺序裁决：

```
机器合同 / 策略 / 规则
        ↓
Action Worker 共用治理
        ↓
项目架构 / 项目边界
        ↓
项目实现文档
        ↓
README / 示例
```

项目规则可以收紧共用规则，但**不得绕过**共用的安全边界、PR 门禁或跨仓库凭据边界。

**AI Review 不是共用门禁**。它只负责审查、建议与发现问题；是否启用、是否成功、发现多少问题，都不能替代或改变确定性的 CI / PR / Security 门禁。

**Security Gate 是共用的硬边界**，由 Action Worker 的确定性检查执行，覆盖公开仓库与私有仓库。

`validate-merge` 是**唯一的合并权限**。AI Review 在确定性门禁结论之后运行，只产生仅供参考的发现。

**Main Write Guard** 是所有受管仓库共用的 main 来源硬边界。无法证明来自合法 PR 合并的 `main` SHA 视为不可信，不得用于发布、部署、公开分发或特权执行。详细规则见 `07_MAIN_WRITE_GUARD.md`。

## 6. Agent 入口

每个受管业务仓库保留两个非常薄的入口文件：

```
AGENTS.md
  ↓
CLAUDE.md
  ↓
Action Worker 共用治理
  ↓
项目专属的权威文档
```

- `AGENTS.md` 只指向下一级，不复制任何规则
- 业务仓库的 `CLAUDE.md` 只列出共用规则的入口、项目的权威文档，以及仅属于该项目的禁止事项

## 7. 机器执行闭环

文档解释规则，但真正的治理由机器合同执行：

```
contracts/   输入输出合同
policies/    确定性策略
rules/       AI 审查策略
.github/actions/  合并执行
workflows/   编排
tests/       治理回归测试
```

**只存在于 Markdown 而没有对应机器约束的重要规则，尚未闭环。**

---

## 8. 平台能力边界

治理目标与 GitHub 套餐功能应分别描述。

Action Worker 门禁对每个受管仓库都成立；原生 GitHub rulesets、分支保护或 Administration API 只在该仓库的套餐与权限范围内启用。**GitHub Free 组织的私有仓库没有强制的 ruleset / 保护分支**，因此在这些仓库中，中央门禁是流程约束，而不是硬性的平台门禁。**平台功能缺失永远不能成为绕过中央门禁的理由**；文档绝不能假设私有仓库已经具备与公开仓库相同的强制保护。

## 9. 文档可读性要求（补充）

### 9.1 机器读取文档（严格）

范围：`SKILL.md`、`contracts/` 机器规则文件、`policies/`、`rules/`、`CLAUDE.md`、`AGENTS.md`、`skills/`。

要求：
1. **英文**
2. **精确且无歧义**：每条规则只能有一种解读；“视情况而定”类含糊措辞禁止
3. **结构化**：使用编号、代码块与显式条件分支（`if...then`），不依赖上下文推断
4. **可验证**：机器可检查的规则必须有对应的合同测试

### 9.2 人类阅读文档（面向新人）

范围：`README.md`、指南、`contracts/README.md`、治理文档中面向人的部分。

要求：
1. **中文**，术语保留英文原词（见 `TERMINOLOGY.md`）
2. **先说明"这是什么"，再说明"怎么做"**：每份文档以一两句话说明用途，不直接进入实现细节
3. **解释每个术语**：dispatch、bootstrap、gate、manifest 等首现时用括号或一句话解释
4. **用示例代替抽象描述**：能用具体示例的不只用规则文字；示例放代码块
5. **不假设读者了解 GitHub Actions**：用日常比喻解释 workflow、runner、dispatch
6. **分层组织**：初学者简要说明 → 维护者技术细节，标题分隔
7. **一段只表达一件事**：超五行未说完改列表或拆小节
