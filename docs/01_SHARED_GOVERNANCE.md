# 共用治理规范

## 1. 权威归属

跨仓库规则只在中央维护。

### ❌ 错误做法 / 反面教材

每个项目复制一套治理规则。

```text
业务仓库甲/docs/治理规范.md
业务仓库乙/docs/治理规范.md
```

### ✅ 正确做法 / 规范范例

中央定义，项目只引用。

```text
action-worker/docs/01_SHARED_GOVERNANCE.md
业务仓库/AGENTS.md → 共用规范 + 项目专属规范
```

## 2. 文档语言

治理说明只写中文。

### ❌ 错误做法 / 反面教材

标题中英混排，正文重复翻译。

```markdown
## 快速开始（Quick Start）
This policy applies to all repositories.
```

### ✅ 正确做法 / 规范范例

中文标题、中文规则、原样代码标识符。

```markdown
## 快速开始
所有受管仓库统一使用中央合并门禁。
```

治理文档不建立双语镜像。二、三级标题只用中文；规则直接陈述，优先给出错误与正确范例。源代码、机器协议、配置键及执行日志保持其原生格式，不改写固定标识符。

## 3. 权威顺序

冲突时以机器合同为准。

### ❌ 错误做法 / 反面教材

让项目说明覆盖共用门禁。

```text
项目文档 → 忽略中央安全门禁
```

### ✅ 正确做法 / 规范范例

按唯一权威顺序裁决。

```text
合同/策略/规则 → 中央共用规范 → 项目边界 → 项目文档 → 示例
```

项目规则可以收紧，不得绕过中央约束。

## 4. 合并门禁

未通过中央门禁不得合并。

### ❌ 错误做法 / 反面教材

把智能体审查当成合并许可。

```text
智能体审查通过 → 合并
```

### ✅ 正确做法 / 规范范例

确定性检查全部成功才授权。

```text
安全校验 + 中央持续集成证据 + 合并请求策略
                ↓
          validate-merge
                ↓
               合并
```

智能体审查只提供建议；它不能替代安全、证据或合并门禁。

中央 CI 的现行主分支通道在控制选择、快照准备、结果发布及后续消费时均须核对合并请求流向；即使提交 SHA 不变，改投未准入的分支也不得继续使用主分支通道。

新产生的合并请求 CI 成功证据在签名状态中记录仓库、合并请求编号、目标分支、基准提交、来源提交及合并快照的摘要。普通合并请求的 CI 复用、等待成功及实际合并前必须核对当前目标分支、实时基准提交及双亲匹配的合并快照；旧范围证据不能授权新合并。已合并历史提交的审计保持兼容。

中央门禁合同为开发分支预留独立的 `Dev PR Governance`、`Dev CI Evidence` 和 `validate-merge-dev` 签名状态。开发分支 CI 成功证据必须同时匹配专属状态及完整 PR 快照；主分支历史状态名称和验证流程保持不变。中央 CI 对公开仓库的显式开发分支 PR 请求使用独立状态及不可变基线控制；普通主分支默认请求仍不接受开发分支 PR，禁止受管分支直接作为来源。开发分支 CI 调度与等待接口支持显式目标分支，独立验证实时快照及状态签名、隔离排队与失败记录；开发分支失败不自动重试原版本的失败。开发分支 CI 不触发主分支后续治理、发布或部署，中央巡检及 PR 治理入口支持公开同仓库受信任开发分支 PR，沿用变更、命名、安全与 CI 门禁并签发独立状态。暂不自动刷新开发任务分支、不运行依赖修复或主分支审查续跑；开发分支治理与合并成功状态均绑定 PR 快照及标题摘要。中央治理在签发后运行只读合并资格核验，写入审计接口校验 squash 提交单亲、CI 合并快照双亲、源码树一致性、精确 PR 归属及合并前签名和完成的中央运行。同一合并作业接入开发分支执行入口，只有中央版本化规则、实际主/开发分支保护、独立可信父提交及实时签名门禁均满足才可授予写令牌。合并后签发独立 Dev Merge Receipt，现有 Intake 等待治理运行成功，再核验完整来源并签发 Dev Write Guard 或记录开发分支事件。当前规则仍封闭，初始化入口通过指定 SHA 的人工授权签发独立凭证，Intake 仅在 dev 实际指向该可信 main SHA、实时封闭保护仍有效且授权未超过 24 小时时签发初始化 Dev Write Guard；不自动创建分支。GitHub 合并 API 只提供 Head 条件写，不能原子约束 Base 或目标分支，启用前仍需专项验证分支流转及并发风险。私有仓库、中央仓库自身的 dev 巡检及正式保护规则尚未启用。

中央定时 Intake 只读比较所有受管仓库的 main/dev 提交祖先关系，使用固定 SHA 并复核两端 HEAD；移动、错误或不可读的快照不作为有效观察。dev 未创建属于正常状态，差异仅供维护者判断，不自动合并、复制、变基或派发跨分支任务。公开运行摘要隐藏非公开仓库的身份和差异明细。分支清理器永久保留 main 和 dev，即使树内容完全相同或源清单声明废弃。

## 5. 主分支可信性

来源未经证明的提交不得发布。

受管分支共用精确合并来源核验，核对目标分支、实际合并提交与合并请求身份，不允许以另一分支的合并记录替代本分支来源证明。该核验仅证明来源，不替代独立的分支门禁及人工授权。主分支历史迁移例外仍局限于原有主分支执行器，开发分支写入审计入口已接入 Intake；开发分支初始化、实际合并和发布权限尚未开放。

写入证明使用分支独立的签名状态名称（`Main Write Guard` / `Dev Write Guard`）；违规事故按分支标题前缀分别查找、去重和处理，即使两个分支具有相同提交 SHA，也不得混用签名或事故处理记录。现有主分支状态及历史事故标题保持不变。

现有普通主分支合并通道不得处理以 `main` 或 `dev` 为来源的合并请求，也不得自动刷新这些分支或将合并请求状态写到其提交上。跨分支流转必须由独立的人工授权路径处理；该路径以及完整的 `dev` 治理尚未启用，不能借普通主分支门禁放行。

跨分支授权复用现有中央 `admin-ops` 管理环境及手动工作流，不新增环境、不修改其现有保护。仅受信 main 的首次人工手动运行可申请授权，必须明确确认并通过中央和目标仓库的当前个人账号管理员权限核验；跨分支流转还必须填写预检输出的完整合并快照摘要，快照变化即拒绝。普通评论、标签、AI 审查、机器人、重跑和自动调度不构成授权。此路径不签发跨分支合并门禁、不执行合并；既有环境原生保护继续生效，用户账号身份不等于物理人工操作证明。

### ❌ 错误做法 / 反面教材

直接写入主分支并部署。

```bash
git push origin HEAD:main
```

### ✅ 正确做法 / 规范范例

合并后校验来源，再执行特权任务。

```text
合并请求 → 中央门禁 → 合法合并 → 主分支来源证明 → 发布/部署
```

`07_MAIN_WRITE_GUARD.md` 定义详细证明规则。私有仓库缺少原生分支保护时仍必须经过中央治理；不得把提醒标签当作强制保护。

## 6. 执行与密钥

重型任务与凭据统一管控。

任务分发合同使用 `target_branch` 与不可变的 `bootstrap_ref` 表达目标分支及源码提交。旧请求未声明分支时固定为 `main`，不得随仓库默认分支变化而改道。当前任务执行器仅准入 `main`，在读取任务凭据前拒绝 `dev`；待独立状态、证据与写入保护完成后再开放开发分支执行。

任务历史状态的分支隔离基础按仓库、项目和目标分支区分产物名、清单及加密认证身份。主分支保留既有产物名称和加密兼容，开发分支使用独立命名且不得查找主分支或旧格式产物；开发分支的并发标识也独立。任务状态命令、私有任务可信准备与终结、传输及发布加密信封均校验同一目标分支；普通任务检出后再次核对源码提交。公开无状态试点继续仅支持主分支。开发分支实际执行、凭据授予及发布目标仍未开放。

### ❌ 错误做法 / 反面教材

业务仓库自建中央任务与密钥回退。

```text
业务仓库 → 自建发布链 → 个人令牌自动回退
```

### ✅ 正确做法 / 规范范例

业务仓库只保留薄入口。

```text
业务仓库入口 → Action Worker → 受限执行器
                         ↓
                  独立最小权限凭据
```

缺少专用凭据必须明确失败。执行合同见 `EXECUTION_CONTRACT.md`，运行器规则见 `RUNNER_POLICY.md`。

## 7. 规则与测试

重要规则必须对应机器校验。

### ❌ 错误做法 / 反面教材

只修改说明文字。

```text
修改治理文档 → 直接合并
```

### ✅ 正确做法 / 规范范例

策略、实现、测试和文档同步。

```text
机器合同/策略 → 校验脚本 → 合同测试 → 治理文档
```

配置名称见 `03_NAMING_CONVENTIONS.md`；变更类型和中文日志见 `04_CHANGELOG_CONVENTIONS.md`。

## 8. 项目责任

业务仓库只维护项目专属内容。

### ❌ 错误做法 / 反面教材

复制组织级命名、门禁和发布规则。

```text
项目规则 = 共用命名 + 共用门禁 + 项目实现
```

### ✅ 正确做法 / 规范范例

项目独立定义产品与运行时。

```text
项目规则 = 产品边界 + 对外协议 + 专属测试 + 实现约束
```

新增共用规则必须先修改 Action Worker；不为每个仓库创建第二份权威。

## 9. 构建、测试和发布的中央归属

共用工程能力必须由中央维护。

组织依赖盘点复用中央每日配置作用域审计及只读安装清单，自动发现可访问的活动仓库，
排除归档、禁用及策略排除项。主分支和开发分支独立读取固定提交对应的 Git 树及清单，
开发分支不存在不视为异常。扫描覆盖常见 npm、Python、Rust 清单及工具版本文件，统计锁文件覆盖，
不执行目标仓库代码，不安装目标依赖，不写入任何仓库。公共依赖声明差异仅作信息报告，
不能证明版本不兼容或锁文件实际解析版本不同；无法解析的声明、截断的树、超限清单、
不可读或发生移动的分支明确计数。公开日志仅展示公开仓库明细，私有仓库仅报告数量。
本阶段不设置中央版本基准、不修改依赖、不新增合并阻断；后续策略及整改需单独通过治理。

### ❌ 错误做法 / 反面教材

业务仓库自行复制完整的测试与发布链。

```text
业务仓库 → 本地构建 → 本地测试 → 本地发布
```

### ✅ 正确做法 / 规范范例

业务仓库提供源码与编译声明，中央统一执行。

```text
产品源码与编译配置 → Action Worker → 可信构建与测试 → 中央门禁
```

共用工程能力只在 Action Worker 中实现；业务仓库仅维护产品源码、锁定依赖、
编译器配置及确实不能外置的产品专属构建参数。业务仓库不可另建独立的 CI、
测试执行器、通用构建器或发布/部署编排，也不得在 PR 内自行降低中央门禁。

- 通用构建器、测试基础设施、可外置的业务回归测试、发布编排及凭据策略归中央。
- 产品专属编译配置（如 `tsconfig.json`、Cargo 清单、依赖锁文件）随源码版本管理。
- 必须在仓库中执行的 Rust crate、桌面 UI、特权基础设施测试可保留，但例外的
  仓库及路径只能在中央 `policies/engineering-ownership.json` 中批准并说明原因。
- 禁止新增项目内 `tests/` 测试源码、`*.test.*` 等测试，以及本地
  `central-ci*` 执行入口；新增可外置测试一律进入 `tests/packs/<pack>/`。
- 业务仓库只能使用 `templates/bridge/` 中可信版本的薄工作流；不得自行新增或
  修改为可执行产品构建、测试和发布的 Actions 工作流。
- 现存未迁移测试属于待收敛债务，不构成新增测试的永久豁免；迁移须先记录基线，
  在中央测试包通过验证后，才可删除业务仓库中的原件。

### 门禁

中央 CI 准备阶段在所有路由（包括原生私有 CI）使用可信 Action Worker、
GitHub 只读比较 API 与 `base/head` 不可变提交运行
`scripts/engineering-gate-api.ts`；Linux 沙箱另以真实 Git 差异运行
`scripts/central-engineering-gate.ts`，在项目源码执行前再次确认。业务 PR 修改自身测试、策略文件或
工作流，不能改变此项判定。新增本地工程基础设施、未经批准的工作流或
新测试文件将使 CI Evidence 失败，`validate-merge` 因而不得放行。

仅改文档不构成豁免。确需新增例外时，必须先在 Action Worker 提交可验证的
中央策略与测试，并说明为何中央无法独立执行，不允许在业务仓库声明例外。
详细执行与迁移见 `05_INTEGRATION_GUIDE.md`、`TEST_PACKS.md`。

### 依赖版本目录

中央建议基准及分类的唯一来源为 `policies/dependency-versions.json`。
工具链和通用工程依赖可以定义候选版本；框架及项目专用依赖按兼容性独立管理，
未列出的依赖默认为项目专用，版本为空表示尚未设定统一基准。两段版本表示次版本系列，
三段版本表示精确候选版本；它们不是已验证的运行时或已解析锁定版本。

每日盘点报告精确声明匹配、差异、待人工判断的范围及例外匹配，并生成按仓库和目标分支独立的整改计划。
只有完整且复核过 HEAD 的扫描结果才生成计划，绑定基准提交、清单文件、文件对象 SHA、当前声明、中央候选版本及最近的锁文件。
现阶段策略区分声明更新、npm 锁文件同步、pnpm 锁文件同步和人工复核；缺少锁文件、同层存在多种锁文件、未知生态及普通依赖范围均需人工复核。
框架和项目专属依赖不强制统一，已批准有效例外不生成整改项。私有仓库仅公布计划数，不公开身份、路径或版本明细。
计划是只读候选任务，不代表已验证兼容性、已生成锁文件或已授权创建 PR；后续执行器须重新验证快照及门禁。
范围、工作区引用和间接依赖不能凭字符串比较认定兼容或不兼容。
未使用某个依赖的仓库不必安装该依赖。各仓库继续保留独立清单与锁文件。
例外必须经中央策略 PR 批准，精确绑定仓库、目标分支、依赖标识和声明值，
提供原因及有效截止日（UTC，含当日），禁止通配、跨分支继承或自动延长。
过期例外不再匹配；公开报告不显示私有仓库的例外身份或内容。

现有组织配置审计提供手动整改入口：默认仅检查，明确确认后自动发现已授予 PR 能力的仓库及现存 main/dev 分支，分别生成整改 PR。
复用 `admin-ops` 及同一管理员身份核验；逐仓库授予短期写令牌，提交前复核完整基准和变更摘要，已有整改 PR 不重复创建，不覆盖任何现有分支。
公开仓库在无 App 或管理员写入凭据的计算作业中同步根清单的中央通用开发依赖及包管理器版本、生成 npm/pnpm 锁文件；受信任作业重新计算计划、校验锁文件与清单的匹配关系后才创建 PR。私有仓库仅通过受限 API 在内存中更新现有运行时声明和可证明无需重新解析的 npm 元数据，逐仓库短期写令牌使用后撤销，不公开身份、路径或制品。需要私有源仓原生沙箱重新解析的依赖、歧义锁文件、独立子项目和复杂目录仍报告待复核，不写入不一致的锁文件。
所有生成的 PR 沿用现有 CI 和合并门禁，不改变发布或跨分支权限。全组织兼容性验证和强制偏离门禁尚未完成。

## 10. 文档结构与维护

文档各归其主。

### ❌ 错误做法 / 反面教材

在多个仓库复制整套规则。

```text
仓库甲/CLAUDE.md = 全套治理规则
仓库乙/CLAUDE.md = 全套治理规则
```

### ✅ 正确做法 / 规范范例

权威规则集中维护，作用域规则逐级补充。

```text
根目录 AGENTS.md = 仓库规则
根目录 CLAUDE.md → AGENTS.md
目录级 AGENTS.md = 本目录适用的增量规则
```

- 组织共用治理集中在 Action Worker 的 docs/；业务仓库引用中央规则，只在本仓库说明产品架构、协议、操作与项目专属约束。
- 仓库根目录的 AGENTS.md 是智能体规则的唯一规范来源。需要目录专属规则时，使用该目录下的 AGENTS.md，只写相对根规则增加的约束。
- 根目录 CLAUDE.md 只保留指向同目录 AGENTS.md 的简短说明，不复制规则。

### 源码隐私防回流

Delta 持续精简的中央授权变量 `AW_DELTA_PRUNE_POLICY` 同时承载隐私约束。先通过既有应用入口、能力、包和依赖清单收敛产品边界，再按需增加 `deniedSourceRules`，每项含精确字面量 `term` 与经审核的完整文件路径 `allowedPaths`。仅允许必要的协议拒绝器、回归测试或历史格式说明引用，禁止通配路径和生产采集例外。中央静态检查针对实际不可变合并候选树执行，未授权引用阻断，公开日志仅输出规则及计数。未配置规则只报告未启用，不视为隐私验收通过；真实启用须由既有授权管理路径配置变量。源码规则是补充防线，不替代依赖清单、协议准入、运行时外联控制和发行扫描。
