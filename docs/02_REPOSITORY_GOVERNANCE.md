# 仓库治理规范

## 1. 仓库设置

所有受管仓库使用中央默认设置。

### ❌ 错误做法 / 反面教材

各仓库手动维护不同的合并方式。

```text
项目甲：允许合并提交
项目乙：允许变基合并
```

### ✅ 正确做法 / 规范范例

从唯一策略文件统一下发。

```text
policies/repository.json
  → 禁用合并提交与变基合并
  → 启用压缩合并与合并后删除分支
```

## 2. 应用权限

共享设置仅由中央授权写入。

### ❌ 错误做法 / 反面教材

使用普通控制令牌修改设置。

```text
AW_CONTROL_TOKEN → 修改仓库设置
```

### ✅ 正确做法 / 规范范例

使用独立管理凭据，缺失即失败。

```text
AW_ADMIN_TOKEN → 应用 policies/repository.json
```

合并前只读预览：

```bash
node scripts/apply-repository-settings.ts <owner/name> true
```

## 3. 合并门禁

仅中央检查有权批准合并。

### ❌ 错误做法 / 反面教材

用智能体审查或本地状态代替门禁。

```text
人工评价通过 → 直接合并
```

### ✅ 正确做法 / 规范范例

全部确定性证据成功后才合并。

```text
安全校验 + 中央持续集成证据 + 合并请求策略
                  ↓
            validate-merge
                  ↓
                合并
```

被取消或过期的运行不得冒充成功证据。

公开仓库的 `main` 必须同时启用 GitHub 强制 Ruleset，明确要求 `validate-merge` 来自 `fongap-bot`（GitHub App ID `5609149`）；Action Worker 负责计算结论，GitHub 负责在合并前强制检查发布来源和结果。不得用只做事后审计的软门禁替代可用的原生分支保护。

## 4. 平台保护

平台保护不可用时仍执行中央规则。

### ❌ 错误做法 / 反面教材

把提醒标签当作平台强制保护。

```text
merge-blocked 标签 → 已禁止合并
```

### ✅ 正确做法 / 规范范例

区分写入前保护与写入后隔离。

```text
公开仓库 → 原生保护 + 中央门禁 + 主分支来源审计
私有仓库 → 中央门禁 + 主分支来源审计
```

免费组织的私有仓库可能缺少强制分支保护。任何未经证明的主分支提交不得进入发布或部署链。

## 5. 规则修改

控制仓库门禁修改必须经人工批准。

### ❌ 错误做法 / 反面教材

由 Agent 或机器人修改规则并自行批准合并。

```text
Agent 修改门禁 → 自动审核通过 → 自动合并
```

### ✅ 正确做法 / 规范范例

任何 Action Worker 控制平面的变更，都要求 `@fongap` 或 `@fongxen` 所属的真实 GitHub 账号通过 Code Owner Review。批准后若继续推送，必须重新获得人工审核；机器人不能自我批准。业务仓库仍使用自动门禁。

```text
控制仓库 PR → CI / validate-merge 通过 → 代码负责人批准最新提交 → 允许合并
```

这是对控制平面采取的保守保护，强于只审核门禁文件。因为 Agent 也可能通过工作流、脚本绕过门禁。

策略、测试、文档必须同时更新。

### ❌ 错误做法 / 反面教材

直接在单仓库修改共用规则。

```text
业务仓库设置 → 新增全局合并例外
```

### ✅ 正确做法 / 规范范例

只修改中央权威及相应测试。

```text
policies/repository.json
  → 治理合同测试
  → docs/02_REPOSITORY_GOVERNANCE.md
```

不得创建第二套仓库治理规则；主分支证明详见 `07_MAIN_WRITE_GUARD.md`。
