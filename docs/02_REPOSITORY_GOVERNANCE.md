# 仓库治理规范

## 1. 仓库设置

所有受管仓库使用中央默认设置。

### ❌ 错误做法 / 反面教材

各仓库手动维护不同的合并方式。

```text
项目甲：允许合并提交
项目乙：允许变基合并
```

### ✅ 正确做法 / 规范范例

从唯一策略文件统一下发。

```text
policies/repository.json
  → 禁用合并提交与变基合并
  → 启用自动压缩合并与合并后删除分支
  → 无须人工或独立 AI 审查批准；草稿 PR 不自动合并
```

权限由 `policies/repository-access.json` 唯一管理。仓库发现只提交基础 PR 授权，不能直接改写 GitHub Actions 变量。

## 2. 应用权限

共享设置仅由中央授权写入。

### ❌ 错误做法 / 反面教材

使用普通控制令牌修改设置。

```text
AW_CONTROL_TOKEN → 修改仓库设置
```

### ✅ 正确做法 / 规范范例

使用独立管理凭据，缺失即失败。

```text
AW_ADMIN_TOKEN → 应用 policies/repository.json
```

合并前只读预览：

```bash
node scripts/apply-repository-settings.ts <owner/name> true
```

## 3. 合并门禁

仅中央检查有权批准合并。

### ❌ 错误做法 / 反面教材

用智能体审查或本地状态代替门禁。

```text
人工评价通过 → 直接合并
```

### ✅ 正确做法 / 规范范例

全部确定性证据成功后才合并。

```text
安全校验 + 中央持续集成证据 + 合并请求策略
                  ↓
    当前 HEAD 的 PR Governance / CI Evidence / validate-merge 签名状态全部成功
                  ↓
         Action Worker 自动 squash 合并（精确 HEAD SHA）
```

被取消或过期的运行不得冒充成功证据。独立 AI Review 仅可作非阻断性建议，不是合并条件；不得要求第二名审核者、代码所有者 Review 或待处理 Review 线程结束后才合并。未获写入权限的外部 PR 仍须先通过对其代码执行权限的信任准入，这不是对可信维护者的第二人审核。

公开业务仓库的 `main` 要求 `validate-merge` 来自 `fongap-bot`（App ID `5609149`）。Action Worker 自身的 `validate-merge` 是 GitHub Actions 自检（App ID `15368`），由同一份策略在应用时识别，不能错误锁定为业务仓库的机器人。GitHub 负责合并前拦截，中央审计不能替代平台硬门禁。

开发分支尚处于准入准备阶段。中央策略为公开仓库预置仅匹配 `refs/heads/dev` 的独立有效规则集，禁止创建、更新、删除及强制推送，无绕过角色；不变更现有主分支及历史分支的保护规则。此为临时封闭保护，不表示开发分支治理已经上线。中央 `policies/rulesets.json` 的 `dev_merge_repositories` 初始为空，只对经过单独授权的公开仓库启用正常保护。启用前须先由维护者完成精确 main SHA 的初始化授权、受控创建及恢复封闭保护，并等待独立 Dev Write Guard 成功；仓库设置执行器在修改规则前核验该证明。正常保护仍禁止创建、删除及强制推送，仅允许通过独立 `validate-merge-dev` 门禁的 squash 合并。未列入名单的仓库保持封闭，不能通过改写共用 dev 模板进行全组织启用。待独立合并证据、写入审计及人工跨分支授权完成验证后，才按维护者授权替换为正常开发分支保护规则并受控创建分支。私有仓库的 GitHub Free 平台限制仍然适用，不得声称已具备原生强制保护。

## 4. 平台保护

平台保护不可用时仍执行中央规则。

### ❌ 错误做法 / 反面教材

把提醒标签当作平台强制保护。

```text
merge-blocked 标签 → 已禁止合并
```

### ✅ 正确做法 / 规范范例

区分写入前保护与写入后隔离。

```text
公开仓库 → 原生保护 + 中央门禁 + 主分支来源审计
私有仓库 → 中央门禁 + 主分支来源审计
```

免费组织的私有仓库可能缺少强制分支保护。任何未经证明的主分支提交不得进入发布或部署链。

GitHub Free 组织的私有仓库还可能无法开启原生 `allow_auto_merge`；此时中央仓库设置应明确报告能力限制，但不视为其他设置失败。独立的 Action Worker 路径仍必须先验证当前 HEAD 对应的三项签名成功状态，使用受限 GitHub App 执行精确提交 squash 合并。受管 `fongap-bot[bot]` 仅当是真正 Bot 身份且分支来自本组织同一仓库时可直接进入 CI，不要求第二名审查者；未知机器人、外部 Fork 继续保留可信准入。

## 5. 规则修改

单人维护，由所有者明确决定门禁变化。

### ❌ 错误做法 / 反面教材

智能体自行调整、删除或放宽门禁。

```text
Agent 发现 CI 红叉 → 自行降低门禁 → 自动合并
```

### ✅ 正确做法 / 规范范例

修改 Action Worker 的门禁、权限、发布来源验证、分支保护及其执行代码之前，Agent 和其他自动化工具必须获得维护者对具体变更的**明确授权**，包括放宽、更换和删除规则。授权可以在对话或现有 PR 中直接作出，不需要第二名审核者、新增 Actions 工作流或另一套审批配置。没有明确授权时，仅允许提出建议和报告问题，不得自行更改相关代码或设置。

```text
发现问题 → 说明拟修改的门禁和影响 → 所有者明确同意
       → PR + 现有 validate-merge → 按授权范围完成合并
```

确认仅覆盖获批的变更范围；涉及额外放宽必须重新确认。保留 GitHub 原生分支保护，且不允许通过修改测试、工作流或脚本间接绕过门禁。这里的明确授权是人员和自动化执行纪律，不应误称为由 GitHub 原生 Ruleset 强制核验的第二套审批。

策略、测试、文档必须同时更新。

### ❌ 错误做法 / 反面教材

直接在单仓库修改共用规则。

```text
业务仓库设置 → 新增全局合并例外
```

### ✅ 正确做法 / 规范范例

只修改中央权威及相应测试。

```text
policies/repository.json
  → 治理合同测试
  → docs/02_REPOSITORY_GOVERNANCE.md
```

不得创建第二套仓库治理规则；主分支证明详见 `07_MAIN_WRITE_GUARD.md`。

受管 `main` 与 `dev` 均不得作为废弃分支清理对象。差异巡检不创建、不删除、不更新受管分支；未经单独人工授权不得执行代码流转。未创建 dev 不构成治理故障。

规则集详细响应的 `bypass_actors` 需要具备规则写权限的读取身份。开发分支授权计划、审批后的复核签发、dev 写入审计、dev 合并及 Beta 发布使用现有 `admin-ops` 环境中的管理凭据，仅对政策允许的仓库规则集执行精确 GET；审批环境及审批历史使用独立 Actions 只读身份；缺失字段或读取权限时拒绝执行，不将权限缺失误判为违规写入。普通 main 合并、main 审计、正式发布、沙箱及 Agent 不接收该凭据。人工审批仍在独立 `branch-transfer` 环境完成，最终签发前重新验证审批和实时保护。管理凭据不作为合并、发布或状态签发令牌。

初始化授权前应在中央仓库 Settings → Environments 创建 `branch-transfer`，配置明确的用户审批人；单维护者按需允许自我审批。环境不存在或 Actions 读取权限不足时，授权计划明确报错并停止，不自动创建无保护环境，不代替人工审批。
